Kubernetes Monitoring with Prometheus & Grafana on AWS EC2

This README documents the complete monitoring setup used in this project.

The goal is that after reading this once, you should be able to recreate the monitoring stack without following a tutorial again.

1. What We Built

We deployed Kubernetes monitoring using:

Prometheus → collects and stores metrics

Grafana → visualizes the metrics

Node Exporter → exposes Linux node CPU, memory, disk, network metrics

kube-state-metrics → exposes Kubernetes object/state information

Alertmanager → handles alerts generated by Prometheus

Prometheus Operator → manages Prometheus-related Kubernetes resources

Helm → installs the complete monitoring stack

The stack was installed using the Helm chart:

kube-prometheus-stack

Architecture:

                    Kubernetes Cluster

2. Important Concept: What Each Component Does

Prometheus

Prometheus is the metrics collection and monitoring system.

It periodically collects metrics from targets.

Example:

CPU usage
Memory usage
Pod status
Node status
Container metrics
Kubernetes object information

Prometheus stores these metrics in its time-series database.

You query Prometheus using:

PromQL

Example:

up

If a target returns:

1

it is reachable.

If it returns:

0

Prometheus cannot successfully scrape that target.

3. Grafana

Grafana is the visualization layer.

Grafana does NOT normally collect Kubernetes metrics itself.

Instead:

Prometheus --> Grafana

Grafana sends PromQL queries to Prometheus and converts the results into:

graphs

tables

gauges

statistics

dashboards

alerts

Simple way to remember:

Prometheus = Collect + Store + Query

Grafana = Visualize

4. Node Exporter

Node Exporter collects metrics from the Linux host/node.

Examples:

CPU
Memory
Disk
Filesystem
Network
Load

It exposes metrics through an HTTP endpoint, commonly:

:9100

Example metric:

node_cpu_seconds_total

This is why we were able to query:

node_cpu_seconds_total

in Prometheus.

5. kube-state-metrics

This is different from Node Exporter.

Node Exporter tells us about the machine.

kube-state-metrics tells us about the Kubernetes objects/state.

Examples:

Pods
Deployments
ReplicaSets
DaemonSets
StatefulSets
Nodes
Namespaces
Services

Example:

kube_pod_info

This gives information about Kubernetes pods.

Remember:

Node Exporter
    ↓
Linux machine metrics

kube-state-metrics
    ↓
Kubernetes object/state metrics

6. Alertmanager

Alertmanager handles alerts generated by Prometheus.

Flow:

Prometheus
    |
    | Alert condition is true
    v
Alertmanager
    |
    +--> Email
    +--> Slack
    +--> PagerDuty
    +--> Other receivers

Alertmanager is NOT the component that collects metrics.

7. Prometheus Operator

The Prometheus Operator makes running Prometheus in Kubernetes easier.

Instead of manually creating and managing every Prometheus configuration, Kubernetes resources can be used.

The kube-prometheus-stack chart installs the operator and several monitoring components.

8. Why Helm?

Helm is the package manager for Kubernetes.

Instead of manually creating many YAML files, we can install the monitoring stack with one Helm release.

Without Helm, we would need to manually manage many resources.

With Helm:

helm install ...

The chart creates the required Kubernetes resources.

18. VERY IMPORTANT: Port Forwarding Is Temporary

This is one of the most important things to remember.

the external access stops.

But:

Port forwarding was only used to access the UI.

means:

        |
        v

23. Understanding Labels

A Prometheus metric is not just a number.

For example:

node_memory_MemAvailable_bytes{
    instance="10.0.0.156:9100",
    job="node-exporter",
    namespace="monitoring",
    pod="kube-prometheus-stack-prometheus-node-exporter-..."
}

The metric name is:

node_memory_MemAvailable_bytes

The labels identify which target the value belongs to.

Think:

metric + labels = unique time series

25. Connect Grafana to Prometheus

Grafana needs Prometheus as a data source.

Go to:

Connections
    ↓
Data sources

Select:

Prometheus

Create/configure the data source.

The important part is the Prometheus server URL.

Inside the Kubernetes cluster, Grafana should communicate with Prometheus using the Kubernetes Service DNS name.

For this setup, the service is:

kube-prometheus-stack-prometheus

Namespace:

monitoring

Port:

9090

A typical internal URL is:

http://kube-prometheus-stack-prometheus.monitoring.svc.cluster.local:9090

Depending on the Helm chart/version, the exact service name can be verified with:

kubectl get svc -n monitoring

Do NOT blindly copy an old service name.

Always verify it.

26. Why Grafana Can Use the Internal DNS Name

Grafana and Prometheus are both running inside Kubernetes.

Therefore they can communicate through the Kubernetes network.

Grafana Pod
     |
     | Kubernetes DNS
     v
Prometheus Service
     |
     v
Prometheus Pod

There is no need for:

Public IP

between Grafana and Prometheus.

This is better than making Prometheus publicly accessible.

32. Kubernetes Metrics vs Node Metrics

This distinction is important in interviews.

Node Exporter

Answers:

How is the Linux machine doing?

Examples:

CPU
RAM
Disk
Network
Filesystem

kube-state-metrics

Answers:

What is the state of my Kubernetes objects?

Examples:

How many pods exist?
Is a deployment available?
How many replicas are desired?
What nodes exist?
What namespaces exist?

Therefore:

Node Exporter
= infrastructure/node metrics

kube-state-metrics
= Kubernetes object/state metrics

33. Why We Need Both

Imagine:

Node CPU = 95%

Node Exporter can tell us that.

But you also want to know:

Which pods are running?
Which deployment owns them?
Which namespace?
How many replicas?

kube-state-metrics provides Kubernetes object information.

Together they give a much better picture.

50. Interview Explanation

If an interviewer asks:

How did you implement Kubernetes monitoring?

Answer:

I deployed the kube-prometheus-stack using Helm in a dedicated monitoring namespace. The stack provided Prometheus, Grafana, Alertmanager, Prometheus Operator, kube-state-metrics and Node Exporter. Node Exporter collects infrastructure-level metrics such as CPU, memory, disk and network metrics from Kubernetes nodes, while kube-state-metrics exposes Kubernetes object and state information such as pods, deployments and nodes. Prometheus scrapes these metrics and stores them as time-series data. I configured Grafana with Prometheus as its data source and used Kubernetes dashboards to visualize CPU, memory, pod and node metrics. For lab access, I used kubectl port-forward to temporarily expose Grafana on port 3000 and Prometheus on port 9090.

51. Common Interview Questions

Q1. What is Prometheus?

Prometheus is an open-source monitoring and time-series database system that collects metrics from targets and lets us query them using PromQL.

Q2. What is Grafana?

Grafana is a visualization and dashboarding platform. It queries data sources such as Prometheus and presents the data using graphs, tables and dashboards.

Q3. Does Grafana collect metrics?

Normally, no.

Prometheus --> collects
Grafana    --> visualizes

Q4. What is Node Exporter?

Node Exporter exposes Linux host metrics such as CPU, memory, disk and network metrics for Prometheus to scrape.

Q5. What is kube-state-metrics?

It exposes metrics about the state of Kubernetes objects such as pods, deployments, nodes, ReplicaSets and namespaces.

Q6. Difference between Node Exporter and kube-state-metrics?

Node Exporter
= machine/infrastructure metrics

kube-state-metrics
= Kubernetes object/state metrics

Q7. What is PromQL?

PromQL is Prometheus Query Language.

Example:

up

Q8. What does up = 1 mean?

Prometheus successfully scraped the target.

Q9. Why use Helm?

Helm simplifies installation and management of complex Kubernetes applications.

Q10. Why use kube-prometheus-stack?

Because it packages and configures the major Prometheus/Grafana Kubernetes monitoring components together.

Q11. Is port-forward permanent?

No.

It is a temporary tunnel mainly useful for development, testing and administration.

Q12. How would you expose Grafana permanently?

Use an appropriate production access mechanism such as:

Ingress
+
Load Balancer
+
TLS
+
Authentication/security controls

instead of relying on kubectl port-forward.
